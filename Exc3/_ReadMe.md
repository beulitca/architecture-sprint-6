Список проблем и рисков:
1. Сервис core-app отображает историческую информацию об оформленных страховках, возможно, позволяет делать расторжения. В связи с этим сервису могут пригодиться данные о продуктах, доступных на момент заключения договора. Для этого может быть полезен Event Sourceing. Это позволит отображать в ранее оформленных продуктах корректные данные об условиях страхования.
2. Расхождения в данных о продуктах между сервисами core-app и ins-comp-settlement из-за редкого и разнесенного по времени обновления локальных резервных копий по продуктам. 
3. Всплекс нагрузки при срабатывании ins-comp-settlement раз в сутки
4. Проблемы с масштабированием, при росте нагрузки на core-app прямо пропорционально возрастет нагрузка на 
 ins-product-aggregator придется масштабировать оба сервиса. Также может возрасти нагрузка на API страховых компаний и превысить лимиты.
5. Из-за роста числа страховых компаний, аггрегация данных будет происходить дольше, из-за чего входящие запросы от core-app и ins-comp-settlement могут сбрасываться по timeout и повторяться, что приведет к нагрузке на сеть и увеличению времени отклика.
6. На схеме просматривается антипаттерн вложенности асинхронного запроса GraphQL к страховым компаниям в синхронные запросы от core-app и ins-comp-settlement
7. В случае недоступности ins-product-aggregator повторные запросы от потребителей его api могут нагрузить сеть, либо же задержка обновления для core-app будет кратной 15 мин, а для ins-comp-settlement суткам. Нет механизма обновить данные по продуктам в локальных базах сервисов оперативно после восстановления.

Рещение:
1. Представлено на схеме.
2. Для сервиса core-app имеет смысл использовать паттерны transactional outbox и, возможно,  Transaction log tailing, т к мы имеем дело с реляционной базой, содержащей и другие данные, и не переходим полностью на ESDB или event sourcing.
3. Добавлять базу в ins-product-aggregator смысла нет, т к сервис играет роль чисто интеграционного.
